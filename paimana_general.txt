One important implementation decision
The Recent Portfolio Changes section should be small. It should not become another dashboard.
Likewise, the Explore section should simply be navigation cards/buttons—not mini versions of the other dashboards.
So the Home page has only three substantive information layers:
What exists? → 5 KPIs 
Where is it? / Where is risk concentrated? → Risk & Density Map 
What changed? → Recent Changes 
Everything deeper gets pushed into the specialized modules.

For each major warning:

This is where SHAP/model explainability + temporal analysis becomes useful.

9. Key Risk Drivers

Priority 2 — Cost Review

This is still decision support, not an autonomous government decision.

Detect → Explain → Recommend → Act → Monitor → Evaluate

1. ACTIVE ALERTS — FILTERING PROTOCOL
A. What the filter operates on
The filtering system should operate on current warning/project state, not simply on raw project records.
The basic unit is:
Warning signal associated with a project during a particular monitoring period.
However, the dashboard should also maintain a unique-project view so that one project with multiple warnings does not get counted multiple times where project counts are being shown.
So internally you can have:
Project
   │
   ├── Warning 1 — Schedule
   ├── Warning 2 — Cost
   └── Warning 3 — Progress
But the dashboard can say:
1 affected project, 3 active warning signals

B. Organisational filters
1. Sector
Select one or multiple sectors.
If multiple sectors are selected:
Sector A OR Sector B
2. Ministry / Department
Multiple selections:
Ministry A OR Ministry B
3. State / UT
Multiple selections:
Tamil Nadu OR Karnataka
4. Implementing Agency
Multiple agencies:
Agency A OR Agency B
Across different dimensions = AND
For example:
Sector = Transport
AND Ministry = Railways
AND State = Tamil Nadu
means:
Transport projects AND Railways projects AND projects in Tamil Nadu.
This is important: never use the “last selected filter wins” behaviour you observed on PAIMANA.

C. Warning Type
This should be a multi-select OR filter.
Possible warning types:
Cost Overrun 
Cost Escalation 
Schedule Delay 
Milestone Delay 
Commissioning-Date Slippage 
Physical Progress Deterioration 
Financial Progress Anomaly 
Physical-Financial Mismatch 
Implementation Slowdown 
Prolonged Inactivity 
Repeated Milestone Failure 
Composite Risk 
Multi-Factor Deterioration 
If:
Warning Type = Cost + Schedule
the system means:
Projects having either a cost warning OR schedule warning.
But you should also support a separate filter:
Multiple Active Warnings
Any 
1 
2+ 
3+ 
Multiple warning categories 
This lets an officer specifically find:
Projects simultaneously suffering from cost + schedule + progress problems.
That is different from selecting multiple warning types.

D. Severity
Keep severity separate from risk score.
Use:
Critical 
High 
Medium 
Low 
Important:
Severity ≠ probability.
A warning with 70% probability isn't automatically more severe than one with 50%.
Severity can consider:
Probability 
Expected impact 
Project size 
Persistence 
Rate of deterioration 
Number of simultaneous warnings 
So:
Probability = likelihood
while:
Severity = seriousness of the warning

E. Risk Band
Separate from warning severity:
Low Risk 
Medium Risk 
High Risk 
Critical Risk 
Why?
Because a project can have:
Overall Risk = High
but its individual:
Schedule Warning = Medium
That distinction is analytically useful.

F. Warning Status
This should filter the state of the warning, not the state of the project.
Recommended:
New 
Active 
Under Review 
Action Initiated 
Monitoring 
Resolved 
Dismissed / Invalidated 
For the default Active Alerts page, I'd make:
Active + New
the default scope, while allowing the user to expand it.
Important distinction
New ≠ Active
A warning can be:
New → Active for 4 months
without being “new” anymore.

G. Warning Recency
This should refer to the warning event, not the latest project data update.
Possible:
Last 7 days 
Last 30 days 
Last 3 months 
Last 6 months 
Custom period 
You should also retain:
First Trigger Date 
Last Trigger Date 
Resolution Date 
These are different concepts.

H. Reporting Period vs Warning Trigger Period
This is one of the most important nuances.
Suppose:
Project's latest PAIMANA update = August 2026
but the warning was first generated in:
June 2026
These shouldn't be treated as the same date.
So distinguish:
Reporting Period
“Show me projects whose latest monitoring data is from August.”
Warning Trigger Period
“Show me warnings that were generated in June.”
Historical Lookback
“Show me projects that experienced a warning at any point in the last six months.”

I. Warning Persistence
This answers:
How long has this warning remained a problem?
Possible filters:
New 
<1 month 
1–3 months 
3–6 months 
6+ months 
Custom duration 
This is useful because:
Critical for 1 week
and
High for 8 months
represent very different intervention situations.

J. Trend / Deterioration
Use:
Improving 
Stable 
Deteriorating 
Rapidly Deteriorating 
Also consider:
Newly Deteriorating
For example:
Medium → High risk
or:
Physical progress deteriorated for three consecutive months.
This is particularly valuable for early warning, because you don't want the system to only identify already-disastrous projects.

K. Predicted Cost Impact
Don't combine this with cost-warning probability.
You can filter by:
Probability
Probability of cost overrun ≥ 70%
and separately:
Expected impact
Predicted additional cost ≥ ₹100 crore
Those are fundamentally different.
A small project might have:
90% probability × ₹5 crore exposure
while a huge project might have:
50% probability × ₹500 crore exposure.
Both deserve different kinds of attention.

L. Predicted Schedule Impact
Similarly:
Probability
Probability of schedule overrun
versus:
Magnitude
Expected delay in months / percentage.
This allows:
High probability of 2-month delay
to be distinguished from:
Moderate probability of 18-month delay.

Project Name
Partial match 
Keyword match 
Autocomplete 
Project ID
Exact match preferred

1. Core Principle
The Sector Analytics dashboard should answer:
“How is infrastructure performance distributed across sectors, and how does a selected sector perform across states and projects?”
Therefore, filters should help the user define the analytical population, while the dashboard itself determines the appropriate comparison dimension.
The filter system should never change the meaning of the dashboard silently.

2. Global Filter Architecture
The global filter bar should contain:
┌─────────────────────────────────────────────────────────────┐
│ Sector │ Ministry │ State/UT │ Agency │ Period │ Status │ Risk │
└─────────────────────────────────────────────────────────────┘
But these filters do not all have equal importance.
Primary filter
Sector
This is the defining dimension of Sector Analytics.
Secondary filters
Ministry / Department 
State / UT 
Implementing Agency 
Reporting Period 
Project Status 
Risk Band 
These narrow the population being analysed.

3. Sector Filter
Sector should be multi-select.
Example:
Sector
☑ Transport
☑ Energy
☐ Education
☐ Health
☐ Railways
...
Selection logic
Multiple sectors:
OR
For example:
Transport + Energy
means:
Show projects belonging to Transport OR Energy.
It should not mean projects that simultaneously belong to both sectors.
Why?
A project normally has one primary sector classification. Therefore AND logic between sectors would often produce zero results or meaningless results.

4. Ministry / Department Filter
Ministry should also support multi-select.
Example:
Ministry / Department
☑ Ministry A
☑ Ministry B
means:
Projects belonging to Ministry A OR Ministry B.
But Ministry operates across the selected sector(s).
Therefore:
Transport + Ministry of Railways
means:
Transport projects associated with Ministry of Railways.
The overall logic becomes:
(Sector = Transport OR Energy)
AND
(Ministry = Railway OR Power)
This distinction is extremely important.

5. State / UT Filter
State/UT should be multi-select.
Example:
Tamil Nadu
Maharashtra
Gujarat
means:
Projects associated with Tamil Nadu OR Maharashtra OR Gujarat.
Combined with other dimensions:
Sector = Transport
AND
State = Tamil Nadu OR Maharashtra
Therefore:
Transport projects in Tamil Nadu or Maharashtra.

6. Implementing Agency Filter
Agency should be available because two projects in the same sector and ministry can still behave very differently depending on the implementing agency.
Example:
Sector       = Transport
Ministry     = Ministry X
Agency       = Agency A / Agency B
means:
Transport projects under Ministry X implemented by Agency A or Agency B.
Important nuance
Agency should not automatically be treated as a top-level hierarchy under Sector.
The relationship is better represented as:
Sector
   ↕
Ministry
   ↕
Agency
rather than:
Sector
   ↓
Ministry
   ↓
Agency
because Sector, Ministry and Agency are different analytical dimensions.

7. Reporting Period
This should be a proper temporal filter.
Possible options:
Reporting Period
├── Latest Available
├── Current Period
├── Previous Period
├── Last 3 Months
├── Last 6 Months
├── Last 12 Months
└── Custom Period
For the Sector Overview, default should probably be:
Latest Available / Current Monitoring Period
because the user normally wants the current state first.
Important distinction
Do not confuse:
Reporting Period
with:
Project duration / commissioning date.
The first describes when the monitoring data was reported.
The latter describes the project's lifecycle.

8. Project Status Filter
Possible values:
Ongoing 
Completed 
Delayed 
On Hold 
Terminated 
Other / Unknown 
But don't automatically make "Delayed" a simple project-status category if delay is actually derived by your system.
If "Delayed" is an AI/model-derived condition, it belongs more appropriately under risk/performance filters.
This distinction matters because:
Administrative project status ≠ analytical project condition.
For example, a project may officially be "Ongoing" while the model identifies a serious schedule-delay risk.

9. Risk Band Filter
Possible:
Risk Band
☐ Critical
☐ High
☐ Medium
☐ Low
This should filter the analytical risk classification, not the warning severity.
Don't mix:
Risk Band
with:
Warning Severity.
They can be related, but they answer different questions.
For example:
A project can have High overall risk 
but currently have only a Medium-severity warning. 
Sector Analytics should preserve that distinction.

10. Filter Logic
This should be a universal rule across the entire dashboard.
Within the same filter
OR
Across different filters
AND
Example:
Sector:
Transport OR Energy

State:
Tamil Nadu OR Maharashtra

Risk:
High OR Critical
means:
Projects that are
(Transport OR Energy)
AND (Tamil Nadu OR Maharashtra)
AND (High OR Critical risk)
This is the cleanest and most predictable logic.

11. No "Last Filter Wins"
This is particularly important given the behavior you observed in the existing PAIMANA public dashboard.
The system should never do this:
User selects:
Sector = Education

then:
Ministry = Coal

→ Education silently becomes "All"
Instead, retain both selections.
If the combination produces no projects:
No projects match the selected filters.
The system should not silently alter the user's choices.

12. Filter Dependency
There can be legitimate dependency between filters.
For example:
Sector = Transport
The Ministry dropdown can then prioritize/show ministries that actually have Transport projects.
Similarly:
Sector = Transport
State = Tamil Nadu
can restrict the available Agency options to agencies actually represented in that filtered population.
But:
Do not silently remove existing selections.
If a previously selected agency becomes incompatible after changing the sector, show something like:
1 selected agency has no matching projects under the current filters.
Then let the user decide whether to remove it.
This is much better than silently resetting it.

13. Cascading Filters — Use Carefully
I would use soft cascading, not aggressive cascading.
Good
Sector → narrows available Ministry/Agency options
Bad
Sector changed
→ automatically deletes Ministry
→ automatically deletes State
→ resets everything
The user should maintain control over their analytical query.

14. Filtered Dataset Must Be Consistent
This is probably the most important technical rule.
Once filters are applied:
Every KPI, chart, comparison, ranking and project table must be generated from the same filtered population.
For example:
Sector = Transport
State = Tamil Nadu
Then:
Project Count
must represent only those projects.
Total Investment
must represent only those projects.
Average Cost Escalation
must represent only those projects.
Risk distribution
must represent only those projects.
State comparison
must represent only the relevant filtered population.
There must never be a situation where:
KPI uses filtered data
but chart uses national data.

15. Unique Projects vs Records
Be explicit about what you're counting.
For example:
Projects: 182
should mean 182 unique projects.
It should not mean:
182 monthly monitoring records.
This becomes especially important because PAIMANA is fundamentally a monitoring system where projects can have repeated monthly updates.
For Sector Analytics:
Project-level metrics
Project Count 
Projects at Risk 
Projects Delayed 
should use unique projects.
Time-series metrics
can use:
monthly records 
reporting periods 
project-month observations 
but the methodology should be explicit.

16. "Latest Period" vs Historical Analysis
This is another important nuance.
If the user selects:
Reporting Period = Latest
then Sector Analytics should describe the current portfolio state.
If the user selects:
Last 12 Months
then the dashboard should allow trend analysis.
Don't accidentally interpret:
12 months of observations
as:
12 × the number of projects.
A project appearing in 12 monthly records remains one project.

17. Filtered Sector Overview
When no sector is selected:
Show all sectors and compare them.
Example:
Transport      428 projects
Energy         391
Water          327
...
The dashboard is essentially a sector comparison view.
When the user selects:
Transport
the interface changes from:
Compare sectors
to:
Understand Transport
This is a deliberate context change.

18. Sector → State Performance
When the user selects a sector:
Sector = Transport
the next interface should treat Transport as the fixed analytical context.
Then State becomes the comparison dimension:
Tamil Nadu
Maharashtra
Gujarat
Karnataka
...
The user shouldn't need to repeatedly select Transport while exploring states.
The UI should clearly show:
Sector: Transport
with an option such as:
Change sector

19. Sector + State → Projects
Once the user selects:
Sector = Transport
State = Tamil Nadu
the project view becomes:
Transport Projects in Tamil Nadu
At this point, the system can provide:
project list 
project risk 
physical progress 
financial progress 
cost escalation 
schedule delay 
warning status 
project search 
and clicking a project should take the user to:
Project Intelligence

20. Direct Project Search
I would include:
Search Project
[ Project name / Project ID ]
Project ID
Prefer exact matching.
Project Name
Allow:
partial matching 
keyword matching 
Example:
metro
could return projects containing "Metro".
Important
Search should respect the current filters.
If:
Sector = Transport
State = Tamil Nadu
then searching:
Metro
should search within that filtered population.

21. Search + Filter Conflict
Never silently override filters.
Example:
Sector = Transport
State = Tamil Nadu

Search = "Dam"
If there are no matches:
No projects matching "Dam" within Transport → Tamil Nadu.
Don't suddenly search all sectors/states.
Give the user the option to:
Clear filters
instead.

22. Clear All / Reset
Have an obvious:
Clear All
or
Reset Filters
button.
This is preferable to users having to individually remove five filters.
Also show active filters as removable chips:
Transport ×
Tamil Nadu ×
High Risk ×
Last 12 Months ×

23. Show the Active Context
The dashboard should always make the current analytical population visible.
For example:
Showing 428 Transport projects across all states
or:
Showing 73 Transport projects in Tamil Nadu · High/Critical Risk
This is extremely useful because otherwise users can easily forget what their charts represent.

24. Zero-Result State
There are three different situations and they should not be confused.
A. No filters
All available projects.
B. Filters produce zero projects
No projects match the selected filters.
C. Projects exist but a particular metric isn't available
Example:
73 projects match, but cost forecast is unavailable for 11.
That should say:
Cost forecast unavailable for 11 projects
rather than treating them as nonexistent.
This is important for an AI analytics system because missing data is not necessarily the same thing as no data.

25. Missing / Insufficient Data
Don't let missing values silently distort sector comparisons.
Suppose:
Transport: 400 projects
Cost forecast available: 350
and another sector has:
Energy: 300 projects
Cost forecast available: 295
If you calculate average predicted cost overrun only on available records, make that denominator clear.
For example:
Avg. predicted overrun: 12.4% (350 projects)
rather than implying that all 400 projects contributed.

26. National Benchmark Context
This is useful for Sector Analytics.
When looking at:
Transport
you may compare it with:
Overall portfolio
For example:
Transport cost escalation: 14.2%
Portfolio average: 10.2%
But the benchmark must be clearly labelled.
Don't make the national portfolio silently change when the sector filter changes.
Use:
Selected Sector
vs.
All-Portfolio Benchmark
That gives the dashboard genuine analytical value.

27. Navigation Should Preserve Context
This is essential.
If the user does:
Sector Analytics
→ Transport
→ Tamil Nadu
→ Project X
Project Intelligence should know the navigation context.
Ideally:
Sector Analytics → Transport → Tamil Nadu → Project X
Likewise, returning should take the user back to the same filtered view rather than resetting the dashboard.

28. Filtered Analytics ≠ Filtered AI Prediction
One subtle architectural point:
Filtering should not retrain or alter the underlying prediction model.
For example:
Sector = Transport
doesn't mean:
Train a new CatBoost model only on Transport.
The dashboard is simply slicing the model outputs and project population.
Model training/retraining is a separate backend process.
This keeps the analytical results consistent.

29. Recommended Final Filter Set
I would actually stop here:
Core
Sector 
Ministry / Department 
State / UT 
Implementing Agency 
Reporting Period 
Analytical
Project Status 
Risk Band 
Search
Project Name 
Project ID / Code 
That's enough.
I would not add 15–20 filters to Sector Analytics. Things like warning persistence, trigger date, predicted cost impact, warning recency, intervention status, etc. belong primarily in Early Warning, where they have operational meaning.

The governing rules I would put at the top of your actual specification
SECTOR ANALYTICS — FILTERING PROTOCOL
Sector is the primary analytical dimension. 
Multiple values within a filter use OR logic. 
Different filter dimensions use AND logic. 
Filters must never silently reset or override one another. 
Filtered KPIs, visualizations, rankings and project tables must use the same filtered project population. 
Project counts refer to unique projects, not monthly monitoring records. 
Reporting Period defines the monitoring-data window and must not be confused with project duration. 
Risk Band is distinct from warning severity. 
Search operates within the currently selected filter context. 
Zero-result combinations must be explicitly reported rather than automatically corrected. 
Filter dependencies may narrow available choices, but must not silently delete existing selections. 
Sector selection becomes the preserved context when drilling into State Performance and Projects. 
Navigation to Project Intelligence should preserve the user's analytical context. 
National/portfolio benchmarks must remain clearly labelled when comparing a selected sector. 
Missing data must be distinguished from projects that do not exist or do not match the filter. 
This is about the level of detail I would use. Early Warning deserves a much more granular filtering protocol because it is an operational triage system; Sector Analytics should remain comparatively clean and analytical.



















Filtering system for ministry analytics :
Yes. Ministry Analytics should follow the same underlying filter philosophy as Sector Analytics, but there are a few important differences because Ministry is the primary analytical dimension and Implementing Agency becomes much more important.
MINISTRY ANALYTICS — FILTERING & INTERACTION PROTOCOL
1. Core Principle
Ministry Analytics should answer:
“How are infrastructure projects performing across ministries/departments, which ministries or agencies require attention, and what is driving their performance?”
Therefore, the filtering system should allow the user to:
compare ministries, 
isolate a particular ministry, 
examine that ministry across sectors and states, 
drill down into implementing agencies, 
and ultimately reach individual projects. 
It is primarily a comparative and organisational analytics interface, not an alert-management system.

2. Global Filter Architecture
Recommended filter bar:
┌──────────────────────────────────────────────────────────────┐
│ Ministry │ Sector │ State/UT │ Agency │ Period │ Status │ Risk │
└──────────────────────────────────────────────────────────────┘

The important difference from Sector Analytics is simply that Ministry is now the main analytical context.

This is the primary filter.

Ministry / Department

...

Sector:
Transport

4. Important: Ministry Is NOT a Hierarchy Above Sector
This is one of the most important conceptual rules.
Do not model the dashboard as:
Ministry
   ↓
Sector
   ↓
State
   ↓
Agency
   ↓
Project
That is too rigid.
Instead:
                  PROJECT
                /    |    \
           Ministry Sector State
                \
                Agency
These are different analytical dimensions associated with projects.
A ministry can have projects across several sectors.
A sector can contain projects belonging to several ministries.
A ministry can also have projects across several states.
Therefore:
Ministry selection constrains the population; it does not redefine the taxonomy of sectors or states.

5. Sector Filter
Sector should be multi-select.
Example:
Sector

☑ Transport
☑ Energy
means:
Transport OR Energy projects.
When combined with Ministry:

7. Implementing Agency — More Important Here
This filter deserves more prominence in Ministry Analytics than it does in Sector Analytics.
Why?
Because Ministry-level performance can hide large differences between implementing agencies.
For example:
Ministry
   ↓
Agency A
   ↓
Agency B
   ↓
Agency C
The Ministry overview might look acceptable overall while one agency is responsible for a disproportionate amount of:

stalled projects, 
risk, 
poor physical progress. 
Therefore:
Agency is the primary drill-down dimension inside Ministry Analytics.
This is why our agreed structure was:
Ministry Overview → Agency Performance → Projects

8. Agency Selection

Example:
Implementing Agency

☑ Agency B
means:
Agency A OR Agency B.
Combined:
Ministry = Ministry X
AND
Agency = Agency A OR Agency B
means:
Projects under Ministry X implemented by Agency A or B.

9. Agency Does Not Have to Be a Simple Child of Ministry
Another important nuance.
In the UI, you can present Agency as a drill-down under the selected Ministry, because that is useful operationally.
But technically/data-model-wise, don't assume:
Every agency belongs exclusively to exactly one ministry.
An implementing agency may have relationships with multiple departments or organisational structures.
Therefore the system should derive agency availability from the actual project/organisational relationships in the data.

Filtering system for state analytics :
Yes. State Analytics should use the same universal filtering rules we established for Sector and Ministry Analytics, but there are a few State-specific nuances—especially around geographic attribution, State vs project location, and the State → Sector drill-down.
STATE ANALYTICS — FILTERING & INTERACTION PROTOCOL
1. Core Principle
State Analytics should answer:
“How is the infrastructure portfolio performing across States/UTs, what sectors are driving that performance, and which projects are responsible?”
Therefore, filters should define the geographic/project population while keeping State/UT as the primary analytical dimension.
This is a comparative analytics interface, not an alert-management interface.

8. Critical State-Specific Nuance: Geographic Attribution
This is probably the most important State Analytics issue.
You need to define exactly what:
“Project in Tamil Nadu”
means.
A project may:
be physically located entirely in one state, 
span multiple states, 
have a national footprint, 
have a project headquarters in one state but infrastructure elsewhere. 
Therefore, you should not casually equate project implementing agency location with project location.
For State Analytics, the geographic dimension should preferably be based on the project's actual geographic coverage/location, using whatever State/UT field or geographic mapping exists in the PAIMANA data.

9. Multi-State Projects
This needs an explicit rule.
Suppose:
Project X operates across Tamil Nadu + Karnataka.
It should be possible for the project to appear when:
State = Tamil Nadu
and
State = Karnataka
if the underlying project genuinely covers both.
But you must avoid accidentally double-counting it as two projects.
Therefore:
State-level project counts must always count unique Project IDs.
A multi-state project can contribute to multiple geographic views while remaining one unique project at the portfolio level.

10. Don't Invent State-Level Cost Allocation
This is even more important.
Suppose a ₹10,000 Cr project spans:
Tamil Nadu + Karnataka.
Unless the source data explicitly provides a state-wise cost allocation, you cannot legitimately claim:
Tamil Nadu = ₹5,000 Cr
Karnataka = ₹5,000 Cr.
Don't manufacture an allocation.
Instead, use one of these approaches:
Option A — Project attribution
Show the full project value in each relevant State view, while clearly stating:
Multi-state project; project-level cost shown in full.
Option B — State-allocated values
Only use this if the underlying data actually provides state-level allocation.
For SIH, Option A is safer unless you have reliable state-level cost allocation data.

11. Avoid Double-Counting in Aggregates
This creates a subtle issue.
If you sum project costs across States:
Tamil Nadu     ₹10,000 Cr
Karnataka      ₹10,000 Cr
you might incorrectly conclude:
₹20,000 Cr portfolio.
If the same ₹10,000 Cr project is present in both states, the true portfolio value is still:
₹10,000 Cr.
Therefore:
State-level views
Can show projects associated with that State.
Cross-State aggregate
Must use unique project IDs and appropriate aggregation rules.
This should be explicitly documented in your backend/data methodology.

Filtering system for data operations & models dashboard :
Yes. For your specification, I’d make the Data & Model Operations nuances fairly detailed because this dashboard controls the integrity of the entire platform.
Data & Model Operations — Nuance Notes
1. General Dashboard Rules
This is an administrative operations dashboard, not an analytical dashboard. 
Its purpose is to manage the data → feature → model → prediction → risk → warning → dashboard pipeline. 
It must not contain unnecessary portfolio-analysis charts that already exist in Home, Sector, Ministry, State, or Early Warning. 
All operations should clearly show their current status: completed, processing, failed, pending, or not required. 
Long-running operations such as training and full refresh must show progress rather than appearing frozen. 
The dashboard must distinguish between an operation being requested and an operation successfully completed. 
A failed operation must not be represented as successful merely because it was initiated. 
Administrative actions that can materially change the live system should require explicit confirmation. 

2. Selection & Filtering Rules
Selection controls here are primarily for administrative operations, not analytical filtering. 
Dataset selection should allow the admin to choose the relevant dataset/source. 
Dataset version selection should allow the admin to select a specific version where required. 
Model selection should allow the admin to choose which model to train, evaluate, deploy, or refresh. 
Model version selection should distinguish between production, candidate, and previous versions. 
Operation-history filtering may include: 
operation type 
dataset 
model 
status 
date/time 
reporting period 
Filters should affect only the displayed operational records unless an operation explicitly uses the selected dataset/model. 
Selecting a dataset must not silently change the production model. 
Selecting a candidate model must not deploy it. 
Clearing a filter must not delete or modify any underlying data. 
No analytical filters such as Sector/Ministry/State should be assumed to apply to the whole operations dashboard. 
If a particular operation is intentionally restricted to a subset of data, that scope must be explicitly shown. 

3. Dataset Management Rules
Every uploaded dataset should receive a dataset version. 
Previous dataset versions should remain identifiable rather than being silently overwritten. 
The system should distinguish between: 
new dataset 
updated dataset 
corrected dataset 
replacement dataset 
A new monthly PAIMANA upload should normally be treated as an update to the existing PAIMANA source, not as an entirely unrelated dataset. 
Uploading a dataset does not automatically make it part of the production data. 
Upload → validation → integration should be treated as separate stages. 
A dataset with validation errors should not enter the master dataset until the issue is resolved or explicitly accepted under an appropriate warning policy. 
The system should preserve the original uploaded file/version for traceability. 
The system should record: 
uploader 
upload date/time 
reporting period 
dataset type 
version 
record count 
validation status 
A new external dataset should not automatically become a model feature merely because it has been uploaded. 
External datasets should first be registered, validated, integrated, and evaluated for usefulness. 

4. Dataset Versioning
Dataset versions must be distinguishable from reporting periods. 
Example: 
Reporting Period: March 2026 
Dataset Version: PAIMANA v1.8 
Re-uploading corrected data for the same reporting period should create a distinguishable version/revision. 
The system should identify which version is currently being used by the production pipeline. 
Historical versions should remain available for reproducibility where practical. 
A model should record the dataset version used for training. 
A prediction refresh should record which dataset version generated the resulting predictions. 
Replacing a dataset version must not silently invalidate historical model records. 

5. Data Validation Rules
Validation must happen before integration. 
Validation should distinguish between: 
critical errors 
warnings 
acceptable missing values 
Not every missing value should automatically cause dataset rejection. 
Required fields should be distinguished from optional fields. 
Duplicate detection should consider the appropriate business key, such as:
Project ID + Reporting Month, rather than simply duplicate rows. 
A duplicate Project ID across different months is not necessarily a duplicate. 
Unexpected columns should be flagged but should not automatically cause rejection if the system supports schema evolution. 
Schema changes should be clearly reported. 
Invalid Project IDs should be separated from genuinely new projects. 
Invalid dates should be rejected or flagged according to severity. 
Numerical validation should identify impossible or suspicious values rather than blindly deleting them. 
Validation results should show how many records are affected, not just “validation failed.” 
The admin should be able to inspect problematic records where appropriate. 
Rejected records should not silently disappear; the system should record why they were rejected. 

6. Data Integration Rules
Only validated/accepted data should enter the master dataset. 
Integration should distinguish: 
new records 
updated records 
unchanged records 
rejected records 
Existing project records should be updated using stable identifiers wherever possible. 
The system must avoid creating duplicate projects because the same project appears in multiple monthly uploads. 
Project-month records should remain uniquely identifiable. 
External datasets should be joined using explicitly defined keys or defensible matching logic. 
Failed joins must be reported. 
The system must not silently fill unmatched external values with fabricated values. 
Match rate should be visible for external datasets. 
A low match rate should trigger a warning before the dataset is used for modelling. 
External data should retain its source and version information after integration. 
The system should distinguish between: 
data successfully integrated 
data uploaded but not matched 
data rejected 
data awaiting integration. 

7. Feature Processing Rules
Feature generation should occur after the relevant data has been integrated. 
Deterministic features should be recalculated when their underlying data changes. 
Time-dependent features must use only information available up to the relevant reporting period when preparing training/evaluation data. 
Future information must not leak into historical training features. 
Features derived from later project outcomes must not accidentally become inputs to earlier predictions. 
Feature versions should be tracked. 
If an external dataset is added, the system should identify which new features it creates. 
Feature processing failure should prevent dependent model/prediction operations from being treated as successful. 
A feature being available in the database does not automatically mean it should be used by every model. 
Different models may have different feature sets. 
The system should maintain a mapping of:
Feature → Source → Processing Method → Model(s) using it. 

8. Model Training / Retraining Rules
Data update ≠ automatic retraining. 
Monthly PAIMANA data can update predictions using the existing production model without necessarily retraining it. 
Retraining should occur according to an explicit policy, such as: 
sufficient new labelled outcomes 
scheduled retraining 
model degradation 
significant data distribution change 
meaningful feature/data changes 
Training should produce a candidate model first. 
A candidate model must not automatically replace the production model. 
Training should record: 
dataset version 
feature version 
model type 
model configuration 
training date 
evaluation dataset/version 
Training failures must not affect the current production model. 
The existing production model should remain available while a candidate is being trained. 
Multiple model types can be evaluated rather than assuming CatBoost is permanently optimal. 
Retraining should be reproducible using the recorded dataset, features, configuration, and model version. 

9. Model Evaluation & Benchmarking Rules
A candidate model should be evaluated against the current production model. 
Model performance should not be judged using only one metric. 
Classification models should consider: 
Precision 
Recall 
F1 
ROC-AUC 
PR-AUC 
Calibration 
False-warning rate 
Regression models should consider: 
MAE 
RMSE 
R² 
For the Early Warning system, lead time is especially important. 
A model with slightly better accuracy but substantially worse warning lead time may not be preferable. 
Evaluation should use time-aware validation where appropriate because this is longitudinal project data. 
Randomly mixing future observations into training can produce misleadingly optimistic performance. 
Performance should ideally be examined across important project groups, such as sectors or project-size ranges, to identify severe weaknesses. 
The system should distinguish statistical improvement from practically meaningful improvement. 
A candidate should not be deployed solely because one metric improved. 
Model calibration matters because predicted probabilities are used in risk/warning decisions. 

10. Production vs Candidate Model Rules
The system should always clearly distinguish:
Production Model
→ currently used by the live platform.
Candidate Model
→ newly trained/evaluated model awaiting approval.
Archived Model
→ previous production model retained for rollback/reference.
Rules:
Only the production model generates normal live predictions. 
Candidate models can be tested without affecting live dashboards. 
Candidate predictions should not overwrite production predictions. 
Deployment must be an explicit action. 
The system should show the performance difference before deployment. 
The previous production model should remain available for rollback. 
Only one model version should normally be designated as production for a specific modelling task at a time. 

11. Model Deployment Rules
Deployment requires explicit confirmation. 
Before deployment, show: 
candidate version 
current production version 
performance comparison 
training dataset 
feature version 
Deployment should not occur if required evaluation has failed. 
A failed deployment must leave the previous production model active. 
After successful deployment, the system should record: 
deployment date/time 
deployed version 
previous version 
deploying administrator 
Rollback should restore the previous known-good model. 
Deployment itself should not automatically imply that all historical predictions were generated by the new model. 
Existing predictions should retain their model-version metadata. 

12. Prediction Refresh Rules
Prediction refresh is different from model training. 
A data update may require prediction refresh without model retraining. 
A model deployment may require predictions to be regenerated using the new production model. 
The system should clearly indicate the scope of the refresh: 
affected projects only 
all projects 
For a production model change, a full relevant prediction refresh should normally be performed. 
Prediction refresh should update the project-level intelligence layer. 
Predictions should then feed into: 
risk calculation 
warning generation 
intervention prioritisation 
aggregate dashboards 
A partially completed refresh should not be presented as a fully refreshed system. 
If the refresh fails halfway, the system should preserve the previous valid production state or otherwise clearly mark the system as partially refreshed. 
The refresh should record the model and dataset versions used. 

13. Risk & Warning Refresh Rules
Updated predictions should trigger recalculation of dependent risk outputs where required. 
Risk calculation should use the approved risk methodology, not arbitrary changes made during an upload. 
Warning thresholds should not silently change because new data was uploaded. 
Warning generation should use: 
prediction outputs 
deterministic indicators 
deterioration signals 
approved warning rules 
A new prediction should not automatically mean a new warning unless the warning criteria are satisfied. 
Resolved warnings should remain historically traceable. 
Changes in risk/warning status should be identifiable after a refresh. 

14. System-Wide Refresh Rules
After a successful refresh, downstream dashboards should consume the same refreshed intelligence layer.
The system should update:
Home / Portfolio Overview 
Sector Analytics 
Ministry Analytics 
State Analytics 
Early Warning 
Project Intelligence 
Rules:
Dashboards should not independently calculate different versions of the same prediction. 
Project-level predictions should have one authoritative source. 
Aggregated dashboards should consume the refreshed project-level outputs. 
If a dashboard refresh fails, that failure should be visible. 
Different dashboards should not show different model versions for the same project unless explicitly intended. 
The system should display the latest successful refresh timestamp. 

15. Atomicity / Failure Rules
This is particularly important for your system.
A pipeline such as:
Upload → Integration → Features → Model → Predictions → Risk → Dashboards
should not leave the platform in an unclear state.
For example, if:
Data integration ✅
Feature generation ✅
Model training ❌
then the system should not replace the production model or claim that the entire pipeline succeeded.
Similarly:
Predictions 80% complete
should not simply be shown as:
System Updated ✅
Instead show:
Refresh incomplete — 80% processed

16. Audit & Traceability Rules
Every important operation should be traceable.
For a prediction, the system should ideally be able to identify:
Project → Data Version → Feature Version → Model Version → Prediction Timestamp
For a model:
Model Version → Training Dataset → Feature Version → Evaluation Results → Deployment Date
For a dataset:
Dataset Version → Upload → Validation → Integration → Features → Models using it
This gives the platform reproducibility and makes the AI system defensible.

17. Historical Data Rules
Historical records should not be unnecessarily overwritten. 
Corrections should be versioned where practical. 
Historical predictions should retain the model version that generated them. 
If a new model produces different predictions for old projects, the system should distinguish: 
previous prediction 
newly recalculated prediction 
Do not imply that the new prediction was what the system predicted historically. 
Historical model performance should remain available for comparison. 

18. Security / Administrative Rules
Because this dashboard can change the live intelligence system:
Uploading data should be an administrative action. 
Model deployment should require appropriate authorization. 
Destructive operations should require confirmation. 
Important operations should be logged. 
The system should identify who performed major operations. 
Failed or rejected operations should also be logged. 
The interface should clearly distinguish preview/testing actions from production actions. 

19. Most Important Overall Rule
The entire dashboard should follow this principle:
Never let an administrative action silently change the live intelligence system.
Every major change should follow an explicit chain:
Select → Validate → Preview → Confirm → Process → Evaluate → Apply → Record
And the system should always make clear:
What changed?
Why did it change?
Which data/model version caused it?
Was the operation successful?
What part of the platform was affected?
That is the level of nuance I'd put into your specification for this dashboard. It is detailed enough to guide Antigravity/backend implementation without turning this admin page into the same huge filtering specification needed for Sector, Ministry, and State Analytics.

Important — Filtering, Search & Data-Selection Logic / Protocol
The filtering system should be treated as a core data-selection and logic layer, not merely as a UI feature. Every dashboard, KPI, chart, ranking, table, prediction, and project list must operate on the same clearly defined filtered dataset.
The existing PAIMANA public dashboard provides filters for Sector, Ministry/Department, States/UTs, Project Cost, and Month & Year, and its project-level data includes Sector Name, Line Ministry, Implementing Agency, Project Code, Project Name, costs, expenditure, physical progress, and commissioning dates. 
Your system can use this as the basic reference, but Project Intelligence should go one step further by adding a dedicated Project Name / Project ID search mechanism, because an officer may already know the project they want to investigate and should not have to reconstruct it through multiple filters.

1. Filters must be cumulative / intersectional
When multiple filters are selected, they should normally operate using AND logic, not "last selected filter wins."
For example:
Sector = Transport
AND Ministry = Ministry of Railways
AND State = Tamil Nadu
means:
Show projects that satisfy all three conditions simultaneously.
The system should not interpret this as:
"The user selected Ministry after Sector, therefore ignore Sector."
Nor should selecting a new filter automatically reset another previously selected filter to All simply because the combination produces few or zero results.
Example
Suppose the user selects:
Sector → Education 
Ministry → Ministry of Coal 
If there are genuinely no projects satisfying both conditions, the correct result is:
No projects match all selected filters.
The system should not silently change:
Sector = Education → All
just to produce some results.
This is particularly important for an official decision-support system because silently changing the user's query can produce a misleading interpretation of the data.

2. Filters should generally work across dimensions using AND logic
For categorical dimensions, the default logic should be:
Sector AND Ministry AND State AND Agency AND other active constraints
For example:
Sector = Transport
Ministry = Ministry of Road Transport & Highways
State = Tamil Nadu
Agency = NHAI
should return only projects satisfying that combined scope.
Within the same filter, however, multiple selections can reasonably use OR logic.
For example:
State = Tamil Nadu OR Karnataka
combined with:
Sector = Transport
means:
Transport projects in Tamil Nadu or Karnataka.
Therefore the overall conceptual logic can be:
(State = Tamil Nadu OR Karnataka)
AND Sector = Transport
AND Ministry = ...
This distinction should be explicitly defined in the backend.

3. Use dependent / cascading filters where appropriate
Filters should be able to become context-aware.
For example, if the user first selects:
Sector = Transport
the Ministry dropdown can preferentially show ministries that actually have Transport projects.

One major recommendation
Do not try to make every one of these calculations a separate “feature” visible on the UI. Many are intermediate computational features used by other calculations or models.
For example:
Progress velocity → progress trend → deterioration → risk → warning → intervention priority
The user may only see “Deteriorating” and the evidence behind it. The underlying velocity, slope, moving average, etc. can remain computational features.
Likewise:
Cost classifier + cost regression → predicted probability + predicted magnitude → expected cost exposure
This keeps your actual dashboards relatively clean while the backend intelligence layer can be extremely comprehensive.
And crucially, I would not commit all the proposed formulas/thresholds/weights as final yet. Your March 2025+ PAIMANA data should be used to test which features actually exist, which are reliable, which have enough longitudinal coverage, and which thresholds/weights/models perform best. The computational architecture above can be your V1 specification, while the exact parameters become part of your later benchmarking/validation phase.
